# 轨迹评测：不能只看最终答案，还要分析模型每一步的决策

## 测试背景
- 测试对象：银行客服 Agent 的 15 条执行轨迹
- 评测维度：Tool Selection / Argument Quality / Answer Groundedness / Stop Appropriateness
- 模型：llama3.1:8b（裁判）
- 特点：不重新执行 Agent，只读取已保存的 JSON 轨迹做评分

## 关键数据
- 15 条轨迹全部 PASS
- 平均总分：4.8/5
- Avg Tool Selection：4.9
- Avg Argument Quality：5.0
- Avg Answer Groundedness：4.9
- Avg Stop Appropriateness：4.7（最低）

## 核心发现

### 发现 1：最终答案对，不代表过程对
**TC10：Account B204 是什么问题？下一步该做什么？**
- Agent 只调用了 `lookup_account_status`，然后直接回答
- 裁判判定 Stop Appropriateness 只有 1/5
- 理由：Agent 停止太早，没有用 `search_docs` 工具检索下一步操作

**这正是轨迹评测的核心价值：发现「最终答案看起来对，但过程有缺失」的问题。**

### 发现 2：工具选择正确，不代表整体合理
**TC11：Can you check my account status?**
- Agent 没有直接调用工具，而是先问用户「请提供账户 ID」
- 工具选择 5/5（缺少账户 ID 时不该乱调工具）
- 但整体分被拉低，因为裁判认为应该等用户提供 ID 后再回复

### 发现 3：Stop Appropriateness 是最容易出问题的维度
- 平均分最低（4.7）
- 说明 Agent 在「什么时候该停」这件事上最不稳定

## 我的结论
1. 轨迹评测把「只看最终结果」升级为「看每一步决策」
2. 四个维度分别评分，能精确定位问题出在哪一步
3. 这比只看最终答案更细，能发现过程缺失的问题

## 和我实习的对应
| 轨迹评测维度 | 我的 Patch 验证 |
|---|---|
| Tool Selection | 补丁是否改了正确的文件/函数 |
| Argument Quality | 补丁的参数、条件、边界处理是否正确 |
| Answer Groundedness | 补丁的修改是否围绕issue进行 |
| Stop Appropriateness | 补丁是否完整进行了修改 |

## 对应岗位要求
- 有 Agent、代码智能、工具调用、多步任务执行的端到端实践经验
- 能够围绕复杂任务设计合理评测方法
- 有 benchmark 建设或维护经验者优先
